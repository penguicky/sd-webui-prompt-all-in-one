Test 9: Regression Analysis - LoRA vs Other Term Types

Critical Investigation: Compare behavior between LoRA terms and other term types to identify why only LoRA terms lose weight values during hover events.

Test Case A: LoRA Term (Problematic)

{models: <lora:detailed_face:1.2> }

Expected Issue: After modifying weight to 1.5, hover events revert to 1.2 or lose weight entirely

Test Case B: Embedding Term (Working)

{style: (embedding_name:1.2) }

Expected Behavior: After modifying weight to 1.5, hover events maintain 1.5

Test Case C: Regular Term (Working)

{mood: (dramatic:1.2) }

Expected Behavior: After modifying weight to 1.5, hover events maintain 1.5

Root Cause Analysis

  • HTML Escaping Complexity: LoRA uses <> requiring complex HTML escaping vs embeddings/regular terms using () with simple escaping
  • Weight Syntax Differences: LoRA internal <lora:name:weight> vs external (term:weight) syntax
  • Processing Path Divergence: LoRA uses _modifyLoRAWeight() vs common.setLayers() for other terms
  • DOM Rendering Pipeline: LoRA uses _highlightLoraSyntax() vs _highlightWeightSyntax() creating different update timing
  • Critical Issue: Race condition between DOM re-rendering and data-term-value attribute synchronization specifically affects LoRA terms due to complex HTML escaping

Fix Applied

  • 🔧 DOM Attribute Synchronization: Added _syncCategoryTermAttribute() method to explicitly update data-term-value attributes after weight modifications
  • ⚡ Timing Fix: Ensures DOM attributes are updated before listener re-setup to prevent stale data retrieval
  • 🎯 LoRA-Specific Solution: Addresses the unique HTML escaping and timing issues that specifically affect LoRA terms
  • 🔍 Consistency Guarantee: Synchronizes categoryTermHoverData with actual DOM state to prevent value mismatches

❌ Hover over <lora:style_name:1.2> → becomes <lora:style_name>

After Fix (Correct Behavior):

✅ Hover over <lora:style_name:1.2> → remains <lora:style_name:1.2>

  • Protected Formats: <lora:name:weight> and <lyco:name:weight>
  • Backward Compatible: Regular terms and embeddings continue to work with external weight syntax like (term:1.2)
